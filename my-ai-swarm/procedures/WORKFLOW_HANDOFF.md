# Handoff 驗證與交接指南 (WORKFLOW_HANDOFF)

> **版本**：v2.0.0 | **更新日期**：2026-01-06 | **用途**：確保每次角色交接都完整、無遺漏

---

## 🎯 概述

每當一個工作階段完成、交由下一個角色時，**必須驗證對方已收到完整資訊且理解清晰**。

此文檔定義了 5 個關鍵 Handoff 點的檢查清單與驗證程序。

---

## 1️⃣ Architect → Developer Handoff

**觸發**：Architect 完成設計計畫

### Architect 提交物清單

```markdown
☑️ 設計計畫文檔，包含：
  ├─ 功能概述（目的、背景）
  ├─ 架構變更說明（新增/修改的組件）
  ├─ API 定義（新端點的簽名、請求/響應格式）
  ├─ 數據庫變更（新增/修改的表、字段）
  ├─ 相依性列表（新增的 NuGet 包、內部依賴）
  ├─ 實裝步驟（分步驟的實裝順序）
  ├─ 測試計畫（需測試的邊界、異常場景）
  └─ 風險識別（已知的風險、假設）

☑️ 參考代碼（若有現成實現可參考）

☑️ 澄清問題列表（若有技術假設待確認）

☑️ Impact Validator 批准（若是高風險決策）
```

### Developer 驗證清單

Developer 收到後，**必須驗證以下項目**。若任一項不符，**立即反饋 Architect，拒絕開始實裝**：

```markdown
□ 設計計畫是否清晰明確？
  └─ 能否一句話總結功能？

□ 實裝步驟是否可操作？
  └─ 是否能明確知道 1. 什麼時候做什麼 2. 應該修改哪些檔案？

□ API 簽名是否完整？
  └─ 方法名、參數類型、返回類型是否明確？

□ 數據庫變更是否明確？
  └─ 若涉及，是否有完整的 migration 說明？

□ 依賴清單是否完整？
  └─ 是否清楚需要新增哪些 NuGet 包、版本號是什麼？

□ 測試計畫是否清晰？
  └─ 是否知道哪些場景必須測試？

□ 是否有不確定的假設？
  └─ 若有，是否已列出待澄清的問題？

□ 是否需要 Impact Validator 評估？
  └─ 若需要，是否已完成評估？

✅ 全部通過 → 確認收到計畫，開始實裝
❌ 任一不通過 → 要求 Architect 補充或澄清
```

### Handoff 確認

```markdown
**Developer 回覆 Architect**：

✅ 確認收到設計計畫
✅ 已驗證所有項目
✅ 理解實裝步驟
✅ [若需要] 已取得 Impact 評估批准
✅ 開始實裝，預期完成日期：[日期]

若有澄清問題，已列出：
1. [問題 1]
2. [問題 2]
（待 Architect 回覆後再開始）
```

## 2️⃣ Impact Validator → Developer Handoff

**觸發**：Impact Validator 完成風險評估並批准

### Impact Validator 提交物清單

```markdown
☑️ 影響評估報告，包含：
  ├─ 依賴關係圖（直接/間接依賴服務）
  ├─ 風險清單
  │  ├─ 破壞性變更風險（API 簽名改變）
  │  ├─ 數據兼容性風險（Schema 變更）
  │  ├─ 效能風險（新查詢是否有 N+1）
  │  ├─ 並發風險（共享狀態、鎖定順序）
  │  └─ 回滾難度（切換成本）
  ├─ 實裝順序建議（分階段、並行化）
  ├─ 監控指標（上線後應監控的數據）
  ├─ 回滾計畫（<5 分鐘內快速回滾）
  └─ 批准決策（approve / conditional / reject）

☑️ 高風險項的緩解策略

☑️ 測試重點建議
```

### Developer 驗證清單

```markdown
□ 實裝順序建議是否清晰可行？
  └─ 是否能按照建議的順序實裝？

□ 風險清單是否完整？
  └─ 是否理解所有識別的風險？

□ 監控指標是否明確？
  └─ 上線後應該監控哪些數據？

□ 回滾計畫是否可行？
  └─ 若上線後發現問題，能否 <5 分鐘回滾？

□ 緩解策略是否可實施？
  └─ 是否有具體的防護措施（特性開關、漸進式發佈等）？

□ 是否有額外的測試建議？
  └─ 是否知道需要重點測試的場景？

✅ 全部通過 → 按建議實裝
❌ 任一不通過 → 要求 Impact 澄清
```

### Handoff 確認

```markdown
**Developer 回覆 Impact Validator**：

✅ 確認收到評估報告
✅ 已理解實裝順序與風險
✅ 同意監控指標與回滾計畫
✅ 開始實裝

若有疑問，已列出：
1. [疑問 1]
（待 Impact 澄清）
```

## 3️⃣ Developer → QA Reviewer Handoff

**觸發**：Developer 完成實裝並通過本地測試

### Developer 提交物清單

```markdown
☑️ 完整的代碼（無 TODO、FIXME）

☑️ 單元測試，包含：
  ├─ 正常流程測試
  ├─ 邊界值測試
  ├─ 異常處理測試
  └─ 測試覆蓋率 > 70%

☑️ 集成測試（若涉及多個服務）

☑️ 本地測試通過報告
  ├─ 功能測試結果
  ├─ 效能測試結果（若涉及）
  └─ 沒有遺留的 Bug

☑️ 變更總結（Commit 訊息或變更說明）
  ├─ 修改檔案清單
  ├─ 實裝細節說明
  └─ 設計決策說明

☑️ 設計計畫（確保實現與計畫一致）

☑️ 高風險決策的 Impact 評估（若需要）

☑️ 代碼註解（複雜邏輯已標註）
```

### QA Reviewer 驗證清單

**QA 收到代碼前，先驗證前置條件**：

```markdown
❌ 必須有的條件（無則拒絕）：
  □ 必須有 Architect 的設計計畫
  □ 必須有本地測試通過的証明
  □ 高風險決策必須有 Impact 評估批准

✅ 若上述條件都滿足，開始審查：

  □ 代碼是否完整（無 TODO、FIXME）？
  □ 邏輯是否正確？
    └─ Null 檢查、邊界值是否處理？
  □ 命名是否清晰？
    └─ 變數、方法名是否遵循約定？
  □ 代碼結構是否清潔？
    └─ DRY 原則、單一職責？
  □ 效能是否合理？
    └─ N+1 查詢、記憶體洩漏？
  □ 安全是否充分？
    └─ SQL injection、權限控制？
  □ 測試是否充分？
    └─ 覆蓋率 > 70%、邊界都有測？
  □ 文檔是否清晰？
    └─ 複雜邏輯是否有註解？
  □ 是否遵循編碼標準？
    └─ 是否通過 Code Analyzer？

✅ 全部通過 → 批准，準備上線
⚠️ 部分問題 → 要求修改（告知必須修與可選修）
❌ 嚴重問題 → 拒絕審查，要求 Developer 重新實裝
```

### Handoff 確認

```markdown
**QA Reviewer 回覆 Developer**：

審查結果：[批准 / 條件批准 / 拒絕]

若條件批准，需要修改的項目：
必須修：
1. [缺陷 1]
2. [缺陷 2]

可選修（建議）：
1. [改進項 1]

修改完成後重新提交。

若批准：
✅ 通過代碼審查
✅ 準備進入記錄階段
```

## 4️⃣ QA Reviewer → Memory Manager Handoff

**觸發**：QA Reviewer 批准代碼

### QA Reviewer 提交物清單

```markdown
☑️ 代碼審查批准簽核
  ├─ 批准日期
  ├─ 審查人簽名
  └─ 審查結論（批准 / 有條件批准）

☑️ 變更摘要
  ├─ 修改的檔案列表
  ├─ 代碼行數統計
  └─ 功能說明

☑️ 測試覆蓋率報告
  └─ 單位測試、集成測試通過情況

☑️ 品質檢查結果
  └─ Code Analyzer 結果（無 Error）

☑️ 性能測試結果（若涉及）
```

### Memory Manager 驗證清單

**Memory Manager 開始記錄前，必須驗證**：

```markdown
❌ 必須有的條件（無則拒絕記錄）：
  □ 是否有 Architect 的設計計畫？
  □ 是否有 QA Reviewer 的批准簽核？
  □ 高風險決策是否有 Impact 評估？

✅ 若條件都滿足，驗證決策記錄信息：

  □ 日期格式是否正確？（YYYY-MM-DD）
  □ ID 是否遞增無重複？
  □ 內容是否簡潔？（30-50 字）
  □ 理由是否充分？（100+ 字）
  □ 代碼位置是否有效？
    └─ Markdown 連結是否指向正確檔案與行數？
    └─ 連結點擊後是否能跳到代碼？
  □ 決策記錄格式是否與表格一致？
  □ 相關檔案同期更新？
    ├─ copilot-instructions.md（若涉及新服務）
    ├─ CONFIG_SYNC_CHECKLIST.md（若涉及流程變更）
    └─ 其他相關文檔

✅ 全部通過 → 記錄決策，更新配置
❌ 任一項缺失 → 拒絕記錄，要求補充
```

### Handoff 確認

```markdown
**Memory Manager 回覆 QA Reviewer**：

✅ 決策已記錄
✅ 決策 ID：#[ID]
✅ 相關檔案已同期更新
✅ 版本號已升級：v[version]

決策記錄完成，工作流程結束。

備註：
- 決策可在 project-memory.md 查詢
- 相關配置已於 copilot-instructions.md 更新
- 月度審計將驗證此決策的完整性
```

## 🔐 Handoff 驗證矩陣

| Handoff 點 | 檢查項 | 傳出方責任 | 接收方責任 |
|-----------|--------|----------|----------|
| A → D | 計畫完整、風險清晰 | 提供完整計畫 | 驗證清晰性 |
| I → D | 實裝順序、監控指標 | 提供詳細報告 | 驗證可行性 |
| D → QA | 代碼完整、本地測試通過 | 完整代碼 + 測試証明 | 驗證品質 |
| QA → M | 批准簽核、變更摘要 | 明確審查結論 | 驗證完整性 |
| M → 完成 | 決策記錄、配置同期 | 完整記錄 | （流程結束） |

## 📋 常見 Handoff 失敗與補救

### 失敗情景 1：Developer 收到計畫，但不清晰

**症狀**：Developer 開始實裝後，發現計畫有歧義

**補救**：
```
1. Developer 列出不清楚的部分
2. 與 Architect 開會討論
3. Architect 更新計畫
4. Developer 重新開始（已做的工作可能需要調整）
```

**防止**：在 Handoff 時就驗證清晰性，不要開始後才發現

### 失敗情景 2：QA 發現品質不達標

**症狀**：測試覆蓋率不足、代碼結構差

**補救**：
```
1. QA 列出具體缺陷
2. Developer 修改代碼
3. Developer 補充測試
4. 重新提交 QA 審查
```

**防止**：Developer 在本地要嚴格執行相同標準

### 失敗情景 3：Memory 無法找到代碼位置

**症狀**：決策記錄的代碼位置連結無效

**補救**：
```
1. Memory 列出無效的位置
2. Developer 提供正確的代碼位置
3. Memory 更新記錄
```

**防止**：在記錄前驗證代碼位置的有效性

## ✅ Handoff 成功標準

一個 Handoff 被視為「成功」的條件：

```
✅ 接收方確認已收到完整信息
✅ 接收方確認理解清晰無歧義
✅ 接收方確認有能力完成下一步
✅ 接收方明確列出（若有）的澄清問題
✅ 雙方達成共識，準備進入下一階段
```

## 📞 Handoff 異常處理

### 若接收方拒絕接收

```
情景：QA Reviewer 發現代碼無設計計畫，拒絕審查

步驟：
1. QA 明確列出缺失項（缺設計計畫）
2. Developer 返回尋求 Architect 幫助
3. Architect 補充或補救計畫
4. 重新提交 QA Reviewer
```

### 若傳出方無法補充

```
情景：Architect 已盡力但仍有技術歧義

步驟：
1. 列出無法確定的項（標記為「待決策」）
2. 與用戶或技術負責人討論
3. 明確決策後，更新計畫
4. 重新開始 Handoff
```
