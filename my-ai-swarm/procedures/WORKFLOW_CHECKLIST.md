# 工作流程檢查清單與標準 (WORKFLOW_CHECKLIST)

> **版本**：v2.0.0 | **更新日期**：2026-01-06

---

## 📋 各角色的前置檢查清單

每個角色收到任務時，必須執行以下檢查。**若任一項不符，立即拒絕並要求補充**。

---

## 1️⃣ Architect 的前置檢查

**觸發**：收到用戶需求時

```
□ 需求是否清晰明確？
  NO → 要求用戶澄清

□ 是否已讀 project-memory.md？
  NO → 暫停，先讀

□ 現有代碼是否被正確理解？
  NO → 執行 search/read 探索

□ 設計計畫是否完整？
  NO → 逐一補完

□ 是否應啟動 Impact Validator？
  YES → 申請評估，等待批准
  NO  → 繼續

□ 是否有不確定的技術假設？
  YES → 列出「澄清問題」，向用戶確認
  NO  → 繼續

✅ 所有項通過 → 產出設計計畫 → 交由 Developer
```

**拒絕回覆模板**：
```
❌ 需求分析中止

原因：[缺失項]

請補充以下信息：
1. [澄清項 1]
2. [澄清項 2]

待補充後重新提交。
```

---

## 2️⃣ Impact Validator 的前置檢查

**觸發**：Architect 申請影響評估時

```
□ 是否收到 Architect 的設計計畫？
  NO → 要求補充

□ 計畫是否包含：服務名稱、API 變更、依賴清單？
  NO → 要求補完

□ 是否有明確的實裝範圍？
  NO → 要求澄清

□ 是否已確認這是「高風險決策」？
  NO → 確認是否真的需要評估

✅ 所有項通過 → 執行影響評估 → 批准/拒絕
```

**拒絕回覆模板**：
```
❌ 評估拒絕

原因：設計計畫不完整

請補充：
1. [缺失項 1]
2. [缺失項 2]

待補充後重新申請。
```

---

## 3️⃣ Developer 的前置檢查

**觸發**：收到 Architect 設計計畫時

```
□ 是否有明確的 Architect 設計計畫？
  NO → 拒絕。要求 Architect 提供計畫

□ 高風險決策是否已經 Impact Validator 評估？
  不確定 → 向 Architect 確認
  NO → 拒絕。要求 Impact 評估

□ 計畫是否包含詳細的實裝步驟？
  NO → 要求 Architect 補充細節

□ 是否理解所有的設計決策？
  NO → 與 Architect 討論，直到清晰

□ 本地開發環境是否已準備？
  NO → 準備環境

✅ 所有項通過 → 開始實裝 → 本地測試通過 → 提交 QA
```

**拒絕回覆模板**：
```
❌ 實裝拒絕

原因：[缺失或不清晰的部分]

請提供：
1. [補充項 1]
2. [補充項 2]

待澄清後重新提交計畫。
```

---

## 4️⃣ QA Reviewer 的前置檢查

**觸發**：Developer 提交代碼審查時

```
□ 是否有 Architect 的設計計畫？
  NO → 拒絕。要求提供設計計畫

□ Developer 是否完成本地測試？
  NO → 拒絕。要求本地測試通過

□ 高風險變更是否已評估（Impact Validator）？
  需要但無 → 拒絕。要求完成評估
  不需要 → 繼續

□ 代碼是否包含單元測試？
  涉及邏輯但無 → 拒絕。要求補充測試
  不需要 → 繼續

□ 代碼提交信息是否完整？（檔案列表、變更說明）
  NO → 要求補充說明

✅ 所有項通過 → 執行代碼審查 → 批准/要求修改
```

**拒絕回覆模板**：
```
❌ 審查拒絕

原因：[缺失項]

請完成以下後重新提交：
1. [補充步驟 1]
2. [補充步驟 2]

責任人：[相應角色]
```

---

## 5️⃣ Memory Manager 的前置檢查

**觸發**：QA Reviewer 批准代碼後

```
□ Developer 是否完成代碼實裝？
  NO → 等待 Developer 完成

□ 代碼是否通過 QA Reviewer 審查？
  NO → 拒絕。要求通過 QA 審查

□ 是否有 Architect 的設計計畫？
  NO → 拒絕。要求提供設計計畫

□ 高風險決策是否已評估（Impact）？
  需要但無 → 拒絕。要求完成評估
  不需要 → 繼續

□ 決策信息是否完整？
  - 日期、ID、內容、理由、代碼位置
  缺失任一 → 要求補充

□ 代碼位置是否有效？
  NO → 拒絕。要求驗證位置正確性

✅ 所有項通過 → 記錄決策 → 同期更新配置 → 完成
```

**拒絕回覆模板**：
```
❌ 記錄拒絕

原因：[缺失項]

請補充以下後重新提交：
1. [補充項 1]
2. [補充項 2]

責任人：[相應角色]
```

## 🔄 Handoff 驗證清單

每當一個階段完成、移交給下一個角色時，**必須驗證以下項目**：

### Architect → Developer Handoff

**Developer 驗證**：
```
□ 設計計畫是否清晰無歧義？
□ 實裝步驟是否詳細可行？
□ 預期的輸入/輸出是否明確？
□ 是否有設計假設需要確認？
□ 是否需要 Impact Validator 評估？（Developer 確認）

全部通過 → 接受計畫，開始實裝
任一不通過 → 反饋 Architect，要求修改
```

### Impact Validator → Developer Handoff

**Developer 驗證**：
```
□ 實裝順序建議是否清晰？
□ 風險緩解方案是否可行？
□ 監控指標是否明確？
□ 回滾計畫是否完整？

全部通過 → 按建議實裝
任一不通過 → 要求 Impact 澄清
```

### Developer → QA Reviewer Handoff

**QA Reviewer 驗證**：
```
□ 代碼是否完整（無 TODO/FIXME）？
□ 本地測試是否通過？
□ 測試覆蓋率是否達標（>70%）？
□ 設計計畫是否被實現？

全部通過 → 開始審查
任一不通過 → 退回 Developer
```

### QA Reviewer → Memory Manager Handoff

**Memory Manager 驗證**：
```
□ 代碼品質是否達標（QA 批准）？
□ 決策信息是否完整？
□ 代碼位置是否有效？

全部通過 → 開始記錄
任一不通過 → 退回 QA 或 Developer
```

## 📊 審查與記錄標準

### 代碼審查標準（QA Reviewer）

| 維度 | Pass 標準 | 檢查項 |
|------|----------|--------|
| **邏輯** | ✅ 實現完整、邊界全覆蓋 | 是否有 null 檢查、異常處理 |
| **品質** | ✅ 命名清晰、結構清潔 | 是否遵循命名約定 |
| **效能** | ✅ 無明顯效能缺陷 | N+1 查詢、記憶體洩漏 |
| **安全** | ✅ 輸入驗證完整 | SQL injection、權限控制 |
| **測試** | ✅ 覆蓋率 > 70% | 邊界、異常是否有測試 |
| **文檔** | ✅ 註解清晰充分 | 複雜邏輯是否有說明 |

### 決策記錄標準（Memory Manager）

| 項目 | 標準 | 驗證方式 |
|------|------|---------|
| **日期** | YYYY-MM-DD | 檢查格式 |
| **ID** | 遞增無重複 | 與表格校對 |
| **內容** | 簡潔 30-50 字 | 計數 |
| **理由** | 充分 100+ 字 | 計數 |
| **代碼位置** | 有效的 markdown 連結 | 點擊驗證 |
| **格式一致** | 與表格格式匹配 | 視覺檢查 |

## ⏱️ 工作流程時間預期

| 階段 | 預期時長 | 備註 |
|------|---------|------|
| 需求分析 → 設計計畫 | 4-8 小時 | 取決於複雜度 |
| Impact 評估 | 2-8 小時 | 涉及依賴掃描 |
| 代碼實裝 | 1-5 天 | 取決於行數與複雜度 |
| 代碼審查 | 4-16 小時 | 變更量與複雜度 |
| 決策記錄 | 30 分 - 4 小時 | 代碼位置驗證 |

---

## 🚨 常見遺漏點與防止方案

| 遺漏 | 後果 | 防止方案 |
|-----|------|---------|
| 跳過 Impact 評估 | 上線後發現大問題 | 檢查清單必檢，不符拒絕 |
| 無單元測試 | 品質無保證 | QA 拒絕無測試的邏輯變更 |
| 代碼位置無效 | 無法追蹤決策 | Memory 記錄前驗證有效性 |
| 決策記錄不完整 | 他人無法快速理解 | 前置檢查確保完整性 |
| 版本號未升級 | 無法判斷更新時間 | Memory 自動檢查版本號 |
