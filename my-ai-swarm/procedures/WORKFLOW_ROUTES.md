# 標準工作流程路由 (WORKFLOW_ROUTES)

> **版本**：v2.0.0 | **更新日期**：2026-01-06 | **架構**：方案 B（5 角色模型）

---

## 🎯 快速判斷樹

```
用戶提出需求
    ↓
┌─────────────────────────────────────────────────────┐
│ 第一層判斷：決策類型                                │
├─────────────────────────────────────────────────────┤
│ ❓ 是新功能 / 新決策？                              │
│    ↓ YES → 第二層判斷                              │
│    ↓ NO  → 是代碼優化 / 重構？                      │
│           ↓ YES → 第二層判斷                       │
│           ↓ NO  → 是緊急修復 / Bug？                │
│                  ↓ YES → 流程 C                    │
│                  ↓ NO  → 詢問用戶                   │
└─────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────┐
│ 第二層判斷：複雜度評估                              │
├─────────────────────────────────────────────────────┤
│ ❓ 變更行數 > 500 或涉及 2+ 個服務？                │
│    ↓ YES → 流程 A（完整版）                        │
│    ↓ NO  → 流程 B 或 C（簡化版）                   │
└─────────────────────────────────────────────────────┘
```

## 📋 三種標準流程

### **流程 A：複雜新功能 / 重大重構**（最嚴格）

**觸發條件**（滿足任一）：
- ✅ 新功能涉及架構變更
- ✅ 服務重構 / 拆分
- ✅ API 簽名變更
- ✅ 依賴庫升級
- ✅ 變更 > 500 行 或涉及 2+ 服務

**參與角色**：Architect → Impact Validator → Developer → QA Reviewer → Memory Manager

**工作流程圖**：
```
1. Architect
   ├─ 讀 project-memory.md
   ├─ 分析現有代碼
   └─ 產出設計計畫 ✅
        ↓
2. Impact Validator
   ├─ 評估跨系統影響
   ├─ 建議實裝順序
   └─ 簽核批准 ✅
        ↓
3. Developer
   ├─ 按計畫實裝代碼
   ├─ 本地測試通過
   └─ 提交審查 ✅
        ↓
4. QA Reviewer
   ├─ 代碼品質審查
   ├─ 測試覆蓋驗證
   └─ 批准 ✅
        ↓
5. Memory Manager
   ├─ 記錄決策日誌
   ├─ 同期更新配置
   └─ 完成 ✅
```

**預計工時**：1-2 週（規劃+實裝+審查）

**Handoff 檢查點**：
| 階段 | 檢查點 | 負責人 |
|------|--------|--------|
| Architect → Impact | 計畫完整性 + 高風險識別 | Impact Validator |
| Impact → Developer | 風險評估批准 + 實裝建議 | Developer |
| Developer → QA | 代碼完成 + 本地測試通過 | QA Reviewer |
| QA → Memory | 審查批准 + 品質達標 | Memory Manager |

---

### **流程 B：中等優化 / 重構**（標準）

**觸發條件**（滿足任一）：
- ✅ 代碼優化 200-500 行
- ✅ 單一服務內的重構
- ✅ 無 API 簽名變更的邏輯改進
- ✅ 文檔 / 註解完善

**參與角色**：Architect → Developer → QA Reviewer → Memory Manager

**工作流程圖**：
```
1. Architect
   ├─ 分析需求
   └─ 產出設計計畫 ✅
        ↓
2. Developer
   ├─ 實裝代碼
   ├─ 本地測試
   └─ 提交審查 ✅
        ↓
3. QA Reviewer
   ├─ 代碼審查
   └─ 批准 ✅
        ↓
4. Memory Manager
   ├─ 記錄決策
   └─ 完成 ✅
```

**預計工時**：3-5 天

---

### **流程 C：緊急修復 / 小型優化**（快速）

**觸發條件**（滿足任一）：
- ✅ Bug 修復 < 200 行
- ✅ 小型優化 < 100 行
- ✅ 文檔修正
- ✅ 緊急故障修復

**參與角色**：Developer → QA Reviewer → Memory Manager

**工作流程圖**：
```
1. Developer
   ├─ 診斷 + 修復
   └─ 本地測試 ✅
        ↓
2. QA Reviewer
   ├─ 快速審查
   └─ 批准 ✅
        ↓
3. Memory Manager
   ├─ 記錄決策
   └─ 完成 ✅
```

**預計工時**：1-2 天

## 🔐 防遺漏檢查點

### Architect 的檢查點
```
收到需求 → 
- [ ] 是否應該啟動 Impact Validator？
     YES → 申請評估
     NO  → 通知 Developer
```

### Developer 的檢查點
```
收到計畫 →
- [ ] 是否有 Architect 規劃？→ NO 拒絕
- [ ] 是否需要 Impact 評估？→ 是否已評估？→ NO 拒絕
- [ ] 代碼完成後 → 提交 QA Reviewer
```

### QA Reviewer 的檢查點
```
收到代碼 →
- [ ] 是否有設計計畫？→ NO 拒絕
- [ ] 是否有本地測試？→ NO 拒絕
- [ ] 高風險變更是否評估？→ NO 拒絕
```

### Memory Manager 的檢查點
```
收到審查批准 →
- [ ] 代碼是否通過 QA？→ NO 拒絕
- [ ] 代碼位置是否有效？→ NO 拒絕
- [ ] 決策信息是否完整？→ NO 拒絕
```

## 📞 工作流程異常處理

### 若某階段遇到問題

| 問題 | 處理方式 |
|------|---------|
| Architect 規劃不清 | 申請澄清 → 重新規劃 |
| Impact 評估發現高風險 | 重新設計 / 調整方案 |
| Developer 無法實裝 | 評估設計可行性 → 修改計畫 |
| QA 發現品質問題 | Developer 修復 → 重新審查 |
| Memory 記錄失敗 | 確認信息完整 → 重新記錄 |

### 若流程中止

```
需求 → Architect → [中止] 
→ 評估是否重新設計
→ 記錄決策原因（為何中止）
→ 存檔備查
```

## 🎯 工作流程遵守承諾

為確保每次都按流程執行，我們承諾：

1. **每個角色 Prompt 中嵌入檢查清單**
   - 收到任務時驗證前置條件
   - 缺失則拒絕並列出缺失項

2. **Handoff 點設置檢查門**
   - 上一步驟必須明確「完成」
   - 下一步驟不能跳過驗證

3. **月度工作流程審計**
   - Memory Manager 每月檢查上月決策是否遵守流程
   - 產出遵守率報告

4. **提需求時明確流程型別**
   - 用戶提需求時，自動判斷流程
   - 確認角色參與順序
